# 트랜잭션과 캐시(@Transactional & @Cacheable) 상호작용 학습

Spring Framework에서 `@Transactional` 어노테이션으로 관리되는 트랜잭션 환경과 `@Cacheable`로 대표되는 캐시 기능이 함께 사용될 때 발생할 수 있는 여러 상황과 주의점을 학습하는 프로젝트입니다.

## 🎯 목적

-   `@Transactional`과 `@Cacheable`의 기본적인 동작 방식을 이해합니다.
-   두 어노테이션이 같은 메소드에 있거나, 혹은 서로 다른 서비스 메소드에서 호출될 때의 동작 순서와 결과를 분석합니다.
-   트랜잭션이 롤백(Rollback)되었을 때 캐시 데이터는 어떻게 되는지, 반대로 캐시에서 읽은 데이터를 트랜잭션 내에서 사용할 때의 주의점은 무엇인지 학습합니다.
-   "읽기 전용 트랜잭션(`readOnly=true`)"과 캐시를 함께 사용할 때의 이점을 이해합니다.

## 🛠️ 기술 스택

*   **Framework**: Spring Boot 3.5.3
*   **Language**: Java 17
*   **Dependencies**:
    *   Spring Web
    *   Spring Data JPA
    *   Spring Cache (기본 추상화)
    *   H2 Database
    *   Lombok

## 🤔 핵심 학습 시나리오

이 프로젝트는 다음과 같은 시나리오들을 코드로 직접 구현하고 테스트하는 데 중점을 둡니다.

1.  **조회 메소드**: `@Transactional(readOnly = true)`과 `@Cacheable`을 함께 사용하여 조회 성능을 최적화하는 경우.
2.  **수정 메소드**: `@Transactional`과 `@CachePut` 또는 `@CacheEvict`를 사용하여 데이터베이스와 캐시의 데이터를 동기화하는 경우.
3.  **문제 상황**: 트랜잭션이 커밋되기 전에 캐시가 먼저 갱신되어 다른 스레드에서 오래된 데이터를 읽어가는 문제(Dirty Read)가 발생할 수 있는 상황과 그 해결 방법.
4.  **롤백과 캐시**: 트랜잭션이 롤백되었음에도 불구하고 캐시 데이터는 변경되지 않아 발생하는 데이터 불일치 문제.

이를 통해 트랜잭션과 캐시의 실행 순서를 명확히 제어하는 것(예: 트랜잭션이 성공적으로 커밋된 후에만 캐시를 갱신)의 중요성을 학습합니다.
